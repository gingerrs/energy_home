# Контракт W1-D

Стан на 29.10.2026: контракт аналітики для погодження командою.
Обсяг: зведення, formatter, тести, HANDOVER і мінімальне підключення до CLI.
Реалізації domain, dataio та core належать їхнім власникам і тут не додаються.

## API

`ReportSummary` — незмінний dataclass із полями:

- `period_start: datetime | None`;
- `period_end_exclusive: datetime | None`;
- `interval_count: int`;
- `energy_kwh: float`;
- `cost_uah: Decimal`.

`build_demo1_summary(profile, tariff) -> ReportSummary` бере часові межі й
кількість інтервалів із domain, а енергію та вартість — із `core.calculate_cost`.
Він не читає файлів, не змінює профіль і не реалізує тарифну формулу.
Винятки залежностей передаються викликачеві.

`format_console_report(summary) -> str` повертає чотири рядки без кінцевого
переносу рядка. Сам нічого не друкує та не викликає core. Дати мають формат ISO
із часовим зсувом; період має межі `[start, end)`, гроші — два десяткові знаки.
Непорожній summary без часових меж відхиляється з `ValueError`.

## Очікувані залежності

API непорожнього профілю відповідає `anna/w1` (`879167d`):

- `len(profile)`;
- `profile.start_time() -> datetime`;
- `profile.end_time() -> datetime` — виключний кінець останнього інтервалу.

Порожні дані приймаються як профіль із `len(profile) == 0` або `None`.
Другий варіант відповідає `load_demo_profile` із `diana/w1-B` (`f9fd00a`):
CSV лише із заголовком повертає `None`. Це не вимагає зміни domain.

Від C потрібен `calculate_cost(profile, tariff)` із результатом, що містить
`total_energy_kwh: float` та `total_cost_uah: Decimal`. Фінальне округлення
вартості належить core. Типи domain і CostBreakdown тут не перевизначаються.

DTO та formatter можна імпортувати без готових A/C. Для непорожнього зведення
потрібен справжній `energyhome.core`; його відсутність не підміняється нулями.

## Порожні й нульові дані

Порожній результат — `ReportSummary(None, None, 0, 0.0, Decimal("0.00"))`.
Часові методи domain і core для порожніх даних не викликаються.
Нульове споживання за наявності вимірювань зберігає справжній період та count.

Приклад для чотирьох 15-хвилинних інтервалів `[1, 2, 0, 1]` kW і навчальної
ставки 2.50 UAH/kWh:

```text
Період: [2026-01-15T00:00:00+00:00, 2026-01-15T01:00:00+00:00)
Інтервалів: 4
Енергія: 1.0 kWh
Вартість: 2.50 UAH
```

## CLI

`report` використовує `dataio.load_demo_profile`, конструктор `SingleZoneTariff`,
`build_demo1_summary` і `format_console_report`. Готовий текст друкує лише CLI.
Фіксоване значення енергії видалено. Відсутній A/B/C дає код завершення 1
і читабельну помилку; бізнес-помилки domain теж передаються користувачеві.
Інші відсутні внутрішні модулі не маскуються як очікувана помилка залежностей.

## Перевірка та межі приймання

`tests/test_analytics.py` — 18 ізольованих тестів D;
`tests/test_cli.py` — 9 тестів парсера та межі інтеграції CLI.
Підставні об'єкти є тільки в unit-тестах і не доводять правильність core.
Попередня перевірка успішного парсингу CLI збережена з ізоляцією command_report;
фактичний розрахунок перевіряється окремим інтеграційним набором.

`tests/integration_analytics.py` — 4 перевірки без mocks: спільний fixture,
порожній CSV, DST і CLI з двома різними наборами потужностей та порожнім файлом.
Запуск: `PYTHONPATH=src python3 -m unittest discover -s tests -p integration_analytics.py -v`.
Якщо A/B/C відсутні, запуск завершується помилкою, а не успішним пропуском.

На момент перевірки main (`53485ca`) не містить domain/dataio/core.
A і B доступні в окремих гілках; C серед віддалених гілок немає.
Фінальне приймання залежить від готових командних компонентів, погодження API,
