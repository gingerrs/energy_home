## Політики очищення

| Ситуація | strict | reject |
|---|---|---|
| Некоректна дата/число, від’ємна або нескінченна потужність, NaN | Запис у rejects і DataImporterError | Запис у rejects, рядок пропускається |
| Дубль, зворотний час або зміщення поза сіткою | Запис у rejects і DataImporterError | Запис у rejects, рядок пропускається |
| Пропущені інтервали на правильній сітці | Запис у gaps і DataImporterError | Запис у gaps, наступне відоме вимірювання зберігається |
| Відсутній файл, неправильний заголовок або зламана структура CSV | Помилка | Помилка |

Перший валідний запис визначає початок часової сітки. Дублікати не замінюють уже прийняте значення. Потік не сортується; пропуски не заповнюються й не вважаються нульовим споживанням. Валідні піки потужності зберігаються.

У `RejectRecord` є `line`, `reason`, `value`. Для помилки розбору CSV `value` — копія сирого рядка; для помилки готового вимірювання — початковий `MeterReading`. Для прогалини `value` — пара UTC-міток `(початок_пропуску, наступний_відомий_час)`, тобто напіввідкритий інтервал.

## API та чанки

`clean_readings(readings, step_minutes=15, mode='strict', report=None)` — лінивий ітератор валідних `MeterReading`. Час нормалізується до UTC через наявний domain.

`validate_readings(readings, step_minutes=15, report=None)` — споживає потік у режимі reject та повертає повний `QualityReport`.

`iter_meter_csv(path, source_config=None, mode='strict', report=None)` зберігає старі виклики W1; за замовчуванням strict. У режимі reject обов’язково передайте QualityReport, щоб журнал залишався доступним. Без нього clean_readings та iter_meter_csv дають DataImporterError. validate_readings сам створює та повертає report.

Номери помилок відповідають фізичним рядкам CSV, включно з порожніми рядками перед записом. Повторювані назви колонок та зламана структура CSV є помилками джерела в обох режимах.

Для послідовних чанків передавайте той самий report та однаковий крок:

```python
report = QualityReport()
first = list(clean_readings(chunk1, 15, 'reject', report))
second = list(clean_readings(chunk2, 15, 'reject', report))
```

`report.last_timestamp` зберігає останнє прийняте вимірювання, а `report.line` — поточний номер. Для окремих викликів clean_readings номери продовжуються з урахуванням заголовка: перше вимірювання має номер 2.

За наявності gaps результат залишається розрідженим потоком вимірювань. Його не можна безумовно передати в конструктор регулярного `LoadProfile`: це приховало б неповноту або спричинило помилку domain. Для аналітики слід зберегти report і враховувати лише відомі інтервали. Старий `load_demo_profile` залишено strict.

## Синтетичний профіль для C та D

`generate_demo_consumption(seed=0)` повертає `(LoadProfile, labels)`.
Кожна мітка — кортеж `(timestamp, device_id, event_type)`; окремої копії класу Event не створюється.

Використано справжні `FixedDevice` та `CyclicDevice` з W2-A: фон 0.25 kW, прилад heater 1.5 kW із запуском на 60 хвилин після першої години, шум у межах ±0.02 kW. Період — 2026-01-15 00:00–04:00 UTC, крок 15 хвилин.

Точні події: 01:00 UTC — heater/on; 02:00 UTC — heater/off. Мітки отримано з параметрів циклу до додавання шуму. Локальний Random(seed) забезпечує повторюваність і не змінює глобальний генератор випадкових чисел.

Перевірено з реальним `detect_events` гілки `feature/diana_w2-C` (`87da049`): і згенерований профіль, і CSV дають рівно ці дві події за on_threshold=1.0, off_threshold=0.5, label='heater'. Код C у зміни B не включено.

## Обмеження та приймання

Прогалини визначаються між відомими вимірюваннями. Без окремо заданого очікуваного періоду неможливо визначити, чи бракує даних перед першим або після останнього запису. Журнал накопичує проблемні записи; самі валідні дані обробляються потоково.

Незалежне review Маргаритою, погодження API та усна передача залишаються кроками фінального приймання.

## Повторне рев’ю

Виправлено два недоліки: reject без доступного журналу тепер заборонено; повторювані CSV-колонки не можуть непомітно підмінити значення. Додано тести цих сценаріїв і повну перевірку strict на всіх межах чанків.

Нові DTO та основні функції перевірки/генерації займають 78 непорожніх рядків із docstrings. Повний diff модуля, включно з адаптацією CSV-коду W1, більший за 80 рядків. Якщо норма 40–80 стосується всієї зміни, а не основного нового компонента, цей формальний пункт потребує узгодження на review.
