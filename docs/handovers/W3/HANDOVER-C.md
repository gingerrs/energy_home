## Рішення до реалізації

Нерівномірність = peak_kw / mean_power_kw. Це робоча пропозиція команди,
а не підтверджена вимога викладача; погодження залишається відкритим.
Для нульового середнього повертається None. Порожній профіль має peak=0,
mean=0, unevenness=None і mean_price=None; для ненульового профілю з
нульовою ставкою mean_price=0.0.

Середня потужність = сума потужностей / кількість рівних інтервалів.
Середня ціна = неокруглена вартість / неокруглена енергія.
Для об'єднання чанків потрібні неокруглені значення, а не сума вже
округлених total_cost. Округлення UAH — один раз на кінцевому результаті,
до копійок за ROUND_HALF_UP; публічний CostBreakdown W1 збережено.

## API

| Функція | Вхід | Результат |
|---|---|---|
| peak_kw | LoadProfile або None | float, kW; 0 для порожніх даних |
| mean_price | CostBreakdown | float, UAH/kWh; None за нульової енергії |
| profile_metrics | profile, tariff | ProfileMetrics: peak_kw, mean_power_kw, unevenness, mean_price |
| compare_tariffs | profile, iterable тарифів | dict[tariff_id, CostBreakdown]; одна функція calculate_cost для всіх тарифів |
| merge_cost_breakdowns | iterable CostBreakdown | один CostBreakdown, без повторного читання records |

`ProfileMetrics` — frozen dataclass. `CostBreakdown` зберігає п'ять полів W1,
їхні float/dict типи та можливість старого конструктора з п'ятьма аргументами.
`calculate_cost` має той самий виклик `(profile, tariff)`; визначення зони й
ставки делегує `Tariff.zone_at` та `Tariff.rate_at`. Для старих rate-only
об'єктів, як у W1-тестах, залишається зона single.

`average_price` зберігає поведінку W1: total_cost / energy_kwh за показаними
округленими значеннями, до 4 знаків; за нульового energy_kwh повертається 0.0.
Нову точну середню ціну дає mean_price — вона використовує неокруглені суми.
Наприклад, 0.01 kW × 15 хв при ставці 2.5 дає total_cost=0.01, energy=0.0025,
average_price=4.0 за старим правилом і mean_price=2.5 за точною формулою.

## Точність і сумісність reducer

У CostBreakdown додано приватні поля `_raw_energy`, `_raw_cost` та `_tariff_config`.
Точні суми зберігаються як Fraction — стандартна бібліотека Python, без нових
залежностей. Записи профілю не зберігаються; reducer тримає лише суми зон
і один знімок конфігурації тарифу, незалежно від кількості records.
Для кожної зони зберігається лише сума енергії та вартості.

Об'єднувати слід результати calculate_cost/merge_cost_breakdowns для однакової
конфігурації тарифу та неперекривних частин. Перевіряється клас і глибокий
знімок атрибутів екземпляра через vars, зокрема id, timezone, ставки та зони.
Однаковий id з іншими параметрами дає ValueError. Різні екземпляри однакового
класу з однаковими параметрами сумісні; пізніші зміни параметрів, навіть
вкладеного списку зон, не змінюють знімок попереднього breakdown.

Службові атрибути також враховуються консервативно. Тариф зі змінним кешем
або іншим службовим станом потребуватиме узгодженого стабільного ключа
конфігурації при інтеграції; поточні SingleZoneTariff і synthetic fixtures
зберігають лише параметри. Це не припущення про ще не інтегровану W3-A.

Старий DTO без точних сум дає ValueError: відновити точну вартість лише з
округлених чисел неможливо. Він придатний для читання та mean_price.
Порожні частини нейтральні й не додають вигадану single-зону. Нульові
спостережені інтервали зберігають справжні зони. Порожній reducer дає нульовий
результат W1. Повторне об'єднання вже об'єднаних результатів зберігає точність.

Приклад: чотири інтервали по 0.01 kW з кроком 15 хв і synthetic rate=1
окремо показують по 0.00 UAH, але разом дають 0.01 UAH. Reducer повертає 0.01,
як і повний профіль. Обидві суми для різних чанків зберігають однакову точність.

Кожна zone_cost округлюється окремо для показу. Сума показаних zone_cost може
відрізнятися на копійку від total_cost; total_cost завжди округлюється один раз
від точної загальної суми. Тому для наступного об'єднання використовувати
сам DTO з приватними точними сумами, а не його показані числа чи DailySummary.
Очищення дублів/прогалин належить B, а не цьому reducer.

## Перевірки

```sh
PYTHONPATH=src python3 -m unittest discover -s tests -v
PYTHONPATH=src python3 -m unittest discover -s tests -p test_core_w3.py -v
PYTHONPATH=src python3 -m energyhome report --input data/demo/meter_15min.csv --tariff single
```

Перевірено на Python 3.12.14: 120 тестів, із них 101 попередній і 19 нових.
[1,2,0,1] kW з кроком 15 хв дає energy=1 kWh, peak=2 kW, mean=1 kW,
unevenness=2, mean_price=2.5 UAH/kWh при synthetic rate=2.5.

Окремо перевірено:

- None, порожній/нульовий профіль, нульову ставку та дуже малу енергію;
- незмінність DTO, старий конструктор CostBreakdown та збереження винятків;
- порівняння двох тарифів, дубльований id, дві/три зони та точні локальні межі;
- кожну межу поділу, вкладені merge, половину копійки та відсутність мутацій;
- потокове споживання reducer без утримання оброблених breakdowns;
- порожні частини до/після даних, вкладені merge та нульові спостереження;
- різні ставки/timezone/класи з однаковим id, однакові конфігурації в різних
  екземплярах і зміну вкладених параметрів після попереднього розрахунку;
- стару average_price на трьох незалежних контрольних прикладах.

Зовнішня перевірка: W3-B із marharyta/w3, коміт 63447d9, на synthetic році
2026: 8760 погодинних записів, chunk_size 1/17/1000. Усі три результати
повністю збігаються з повним CostBreakdown: 8863.122 kWh, 18468.58 UAH;
rejects=0, gaps=0. Пікова пам'ять tracemalloc приблизно 66/54/615 KiB відповідно
для всього перевірочного pipeline, не лише reducer. Це вимір конкретного
сценарію, не універсальна гарантія швидкодії чи пам'яті.

## Межі приймання

У main c992241 ще немає TwoZoneTariff/ThreeZoneTariff задачі W3-A. Тести
використовують SyntheticTariff лише як fixture; його ставок не представляємо
як офіційні. Production core не копіює логіку тарифних зон і готовий до API A.
Приймання з реальними класами W3-A потрібне після їх інтеграції.

У core додано 80 непорожніх рядків diff, включно з імпортами й docstrings;
тести й Markdown пораховані окремо. Зміна calculate_cost потрібна для точного
накопичення та підтримки зон; стороннього рефакторингу Event/detect_events немає.

викладача щодо формули та усна передача ще попереду. Статус Done не заявлено.
