База: `main`, `79f916a`. Гілка: `feature/andrii-w3-A-tariffs`.
Задача: [W3-A](https://app.notion.com/p/3f57884616a381cb95c6f689a2a6fcd5).

## Результат і межі

У `domain.py` додано `TariffZone`, `TwoZoneTariff`, `ThreeZoneTariff`,
`TariffValidationError` і чисту фабрику `tariff_from_config`.
Нові тарифи використовують наявні `Tariff.rate_at` та `Tariff.zone_at`.
Публічний конструктор `SingleZoneTariff` і реалізація `calculate_cost` збережені.

`config/tariffs.json` містить три явно синтетичні навчальні конфігурації,
`config/tariffs.schema.json` — їхню структурну JSON Schema Draft 2020-12.
Це не чинні ціни постачальника. Ставки задаються явно в UAH/kWh.
Офіційні ставки можна додавати лише з перевіреним джерелом та датою дії.

## API

```python
from energyhome.domain import TariffZone, TwoZoneTariff

tariff = TwoZoneTariff(
    'two_zone', 'Synthetic example', 'Europe/Kyiv',
    [TariffZone('night', 1380, 420, 1.25), TariffZone('day', 420, 1380, 2.5)],
)
```

Конструктори обох зонних тарифів мають однаковий підпис:
`(tariff_id, name, timezone_name, zones: Iterable[TariffZone])`.

`TariffZone(zone_id, start_minute, end_minute, rate)` — frozen dataclass зі slots.
Початок — ціле число 0…1439, кінець — 0…1440; bool і дробові числа не приймаються.
Межі напіввідкриті `[start, end)`. `start > end` означає перехід через опівніч;
рівні межі відхиляються як неоднозначний/порожній інтервал.
Наприклад, 23:00–07:00 = `[1380, 420)`, а 00:00–24:00 = `[0, 1440)`.

TwoZoneTariff підтримує саме `day` і `night`, ThreeZoneTariff — `day`, `night`,
`peak`. Одна зона може мати кілька інтервалів, але ставка в них має збігатися.
Весь локальний день має бути покритий рівно один раз; прогалини, перекриття,
пропущені або невідомі ідентифікатори відхиляються при створенні тарифу.
Ставки — скінченні невід'ємні int/float, bool не приймається; нуль дозволений.

`rate_at(timestamp) -> float` і `zone_at(timestamp) -> str` приймають лише
timezone-aware datetime. Timestamp трактується як момент часу і переводиться
в явну IANA-зону тарифу. Зони визначаються за локальним годинником із точністю
до хвилини: 06:59:59.999999 ще належить інтервалу, який закінчується о 07:00.
При повторенні години обидва моменти з однаковим локальним часом отримують
однакову зону; у пропущену годину UTC-профіль не створює вимірювань.

Немає змінного кешу: виклики не змінюють стан, а правила зберігаються як
канонічні tuples незмінних об'єктів. Вхідні списки та JSON-словники не утримуються.
Це сумісно зі знімком `vars(tariff)` у наявному `merge_cost_breakdowns`.

## Конфігурації

Читання файлу залишається відповідальністю B/E. Domain не читає файлів:

```python
import json
from pathlib import Path
from energyhome.domain import tariff_from_config

config = json.loads(Path('config/tariffs.json').read_text(encoding='utf-8'))
tariffs = [tariff_from_config(key, config['tariffs']) for key in config['tariffs']]
```

Фабрика приймає `tariff_id` і вже розібраний словник `config['tariffs']`.
Ключ словника стає `tariff_id`; поле `type` вибирає `single`, `two_zone` або
`three_zone`. Решта полів відповідає конструкторам: `name`, `timezone_name`,
`rate` для single або `zones` для зонних тарифів.

Schema перевіряє структуру, поля та діапазони. Domain додатково перевіряє
IANA-зону, точне покриття доби, ставки повторюваних зон і допустимі zone ids.
Фабрика не валідує службові поля всього JSON-документа: вона отримує тільки
реєстр тарифів. JSON Schema не є runtime-залежністю пакета.

Помилки нових класів і фабрики — `TariffValidationError`, який одночасно є
`TariffError` і наявним `ValidationError`. Це дозволяє C/E перехоплювати
тарифні помилки, а критеріям W3-A — перевіряти ValidationError.
Ієрархія старих винятків, зокрема device-oriented ValidationError, не змінена.

## Контрольні приклади та перевірка

```sh
python -m pip install .
python -m unittest discover -s tests -p test_tariffs_w3.py -v
python -m unittest discover -s tests -v
```

На Python 3.12.3 після звичайного wheel-встановлення проходять 176 тестів:
149 попередніх і 27 нових W3-A. `pip check` не знаходить зламаних залежностей.
Окремим стандартним валідатором перевірено саму JSON Schema, усі три приклади
та відхилення дев'яти структурно некоректних конфігурацій. Для цієї QA-перевірки
jsonschema встановлено лише в тимчасове середовище, не в залежності проєкту.

Нові 27 тестів перевіряють усі хвилини зимової й літньої доби, точні межі,
обидва переходи DST, різні часові пояси одного моменту, помилкові параметри,
нульову ставку, незмінність зон, копіювання та сумісність зі старим single API.
Інтеграція викликає справжні core, аналітику і графік; модулі B/C/D/E не змінюються.

Для 24 інтервалів по 1 kW тривалістю годину навчальні конфігурації дають:

| Тариф | Енергія | Вартість | Енергія за зонами |
|---|---|---|---|
| single | 24 kWh | 60.00 UAH | single: 24 |
| two_zone | 24 kWh | 50.00 UAH | night: 8, day: 16 |
| three_zone | 24 kWh | 45.00 UAH | night: 8, day: 11, peak: 5 |

На локальній добі переходу DST three_zone дає 23 kWh / 44.00 UAH навесні
та 25 kWh / 46.00 UAH восени при тій самій потужності 1 kW.
Добове покриття в обох випадках — 100%. Підсумки повного профілю збігаються
з core reducer для кожного з 23 способів поділу звичайної доби.

Підключення нового JSON до CLI належить W3-E; наявний CLI поки читає
`config/tariffs.demo.json`. Для C/D доступні ті самі `zone_at`/`rate_at` вже зараз.
Для інтервалу, який перетинає тарифну межу, core використовує ставку на його
початку. Для точного розподілу за зонами сітка профілю має збігатися з межами;
зміна інтегратора інтервалів не входить у W3-A.

API та усна передача. Робочий код і зелені тести не підміняють ці кроки.
